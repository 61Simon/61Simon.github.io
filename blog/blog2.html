CSS Animations That Don't Kill Performance

A practical guide to smooth scroll animations, will-change, transform-based motion, and where most developers go wrong.

Every developer has seen it: a beautiful website that stutters when you scroll. The culprit is almost always the same — animating the wrong CSS properties.

This isn't a theoretical article. These are lessons from real projects, including my Hot Wheels Market catalog, where smooth animation on a dark UI made or broke the experience.

The Golden Rule: Only Animate transform and opacity

When the browser renders a page, it goes through several stages: layout, paint, and composite. Some CSS properties force the browser to recalculate layout on every frame. Others can be handled entirely by the GPU.

Only two properties can be animated without triggering layout or paint:

  • transform — moves, scales, rotates, skews
  • opacity — fades elements in and out

Everything else — width, height, top, left, margin, box-shadow — forces the browser to repaint and potentially re-layout the entire page. At 60fps, you have 16 milliseconds per frame. Layout recalculations eat that budget fast.

💡 Rule of thumb: If your animation touches geometry (size, position) or visuals (color, shadow), it's probably expensive. Use transform instead.

Bad vs. Good

/* ❌ Bad: triggers layout on every frame */
.box {
    transition: left 0.3s ease, width 0.3s ease;
}

/* ✅ Good: GPU-composited, no layout */
.box {
    transition: transform 0.3s ease, opacity 0.3s ease;
}
.box:hover {
    transform: translateX(20px) scale(1.05);
}

Use will-change — But Don't Abuse It

will-change tells the browser to promote an element to its own compositor layer before the animation starts. This eliminates the initial jank.

.card {
    will-change: transform, opacity;
}

But here's the trap: every layer consumes GPU memory. If you slap will-change on 50 elements, you'll crash performance instead of improving it.

My approach: apply will-change only to elements that animate frequently — parallax images, hover cards, scroll-triggered sections. Remove it after the animation completes if the element is no longer moving.

/* Apply only during hover */
.card {
    transition: transform 0.3s ease;
}
.card:hover {
    will-change: transform;
}

Scroll Animations: IntersectionObserver

Scroll-triggered animations are popular, but most implementations use scroll event listeners that fire dozens of times per second. That's a performance killer.

Use IntersectionObserver instead — it fires only when elements enter or leave the viewport:

const observer = new IntersectionObserver((entries) => {
    entries.forEach(entry => {
        if (entry.isIntersecting) {
            entry.target.classList.add('visible');
            observer.unobserve(entry.target); // stop watching
        }
    });
}, { threshold: 0.15 });

document.querySelectorAll('.fade-in').forEach(el => {
    observer.observe(el);
});
.fade-in {
    opacity: 0;
    transform: translateY(30px);
    transition: opacity 0.7s ease, transform 0.7s ease;
}
.fade-in.visible {
    opacity: 1;
    transform: translateY(0);
}

The unobserve call is crucial — once an element has animated in, there's no reason to keep watching it. This frees up resources for elements still waiting.

The Parallax Trap

Parallax effects look great but are notoriously expensive. A naive implementation updates style.transform on every scroll event, causing layout thrashing.

The fix: batch updates with requestAnimationFrame:

let ticking = false;

window.addEventListener('scroll', () => {
    if (!ticking) {
        requestAnimationFrame(() => {
            const y = window.scrollY;
            heroImage.style.transform = `translateY(${y * 0.15}px)`;
            ticking = false;
        });
        ticking = true;
    }
});

This ensures the browser only updates the transform once per frame, not once per scroll event. On mobile, this is the difference between smooth and unusable.

Real Numbers

On the Hot Wheels Market, after switching from scroll listeners to IntersectionObserver and transform-based animation:

  • Frame rate during scroll: 42fps → 59fps
  • Total blocking time: 180ms → 40ms
  • CPU usage while scrolling: cut roughly in half

Same visual result. Dramatically better experience.

Quick Checklist

  1. Animate only transform and opacity
  2. Use will-change sparingly — only on elements that actually animate
  3. Use IntersectionObserver, not scroll listeners
  4. Batch scroll updates with requestAnimationFrame
  5. Unobserve elements after their animation completes
  6. Test on a real mobile device, not just DevTools throttling

Performance isn't a feature you add later. It's a habit you build from the first line of CSS. Get these fundamentals right, and your animations will feel effortless — on every device.
