How I Built the Hot Wheels Market

Lessons from building a full e-commerce catalog with vanilla JavaScript — filtering, search, performance, and design decisions behind the dark UI.

When I started building the Hot Wheels Market, I had one rule: no frameworks. No React, no Vue, no jQuery. Just HTML, CSS, and vanilla JavaScript.

Was it a smart decision? Honestly, it depends. But it taught me more about JavaScript than any framework ever could. Here's how I built it, what I learned, and where I'd do things differently.

The Challenge

Hot Wheels collectors need to browse hundreds of models. Existing collector sites are either outdated forums or clunky mobile apps. The goal was simple: build a fast, modern catalog that works perfectly on any device — and can be deployed anywhere with zero backend.

The requirements were clear:

  • Instant search across product names and series
  • Multi-criteria filtering (by series, rarity, price range)
  • Shopping cart with localStorage persistence
  • Dark UI that makes the car photos pop
  • No build step, no dependencies — just static files

Why Vanilla JavaScript?

Let me be honest: React would have been faster to build. But vanilla JS forced me to solve problems at the foundation level — and that's where the real learning happens.

The biggest win was performance. No framework overhead, no virtual DOM, no hydration. The entire site loads in under a second, even on slow connections. That matters when your audience is browsing from a phone at a collector convention.

💡 Lesson learned: Frameworks solve problems you don't have yet. For a catalog with a few hundred items, vanilla JS is not just viable — it's optimal.

Building the Filter System

The filter system is the heart of the catalog. Here's the core logic:

function filterProducts() {
    const searchTerm = searchInput.value.toLowerCase();
    const activeSeries = [...document.querySelectorAll('.series-filter:checked')]
        .map(cb => cb.value);
    const minPrice = parseFloat(minInput.value) || 0;
    const maxPrice = parseFloat(maxInput.value) || Infinity;

    return products.filter(product => {
        const matchesSearch = product.name.toLowerCase().includes(searchTerm)
            || product.series.toLowerCase().includes(searchTerm);

        const matchesSeries = activeSeries.length === 0
            || activeSeries.includes(product.series);

        const matchesPrice = product.price >= minPrice
            && product.price <= maxPrice;

        return matchesSearch && matchesSeries && matchesPrice;
    });
}

The key insight: filtering should never touch the DOM directly. First compute the filtered array, then render. This keeps logic and presentation separate — and makes debugging 10× easier.

The render function

Rendering is where most vanilla JS projects get messy. My approach: build HTML as a string, then inject once.

function renderProducts(products) {
    if (products.length === 0) {
        grid.innerHTML = '<div class="empty">No cars found</div>';
        return;
    }

    grid.innerHTML = products.map(product => `
        <article class="product-card" data-id="${product.id}">
            <img src="${product.image}" alt="${product.name}" loading="lazy">
            <h3>${product.name}</h3>
            <span class="series">${product.series}</span>
            <span class="price">${formatPrice(product.price)}</span>
        </article>
    `).join('');
}

Why innerHTML instead of createElement? For this use case, it's faster and more readable. When you have hundreds of items, string concatenation wins. Just be careful with user-generated content — always sanitize.

The Dark UI Decision

The dark theme wasn't just aesthetic. Hot Wheels cars are colorful, glossy, and often photographed on white backgrounds. A dark UI makes those colors pop — it's the same principle museums use when displaying jewelry.

I used CSS custom properties for the entire color system:

:root {
    --bg: #0a0a0a;
    --card: #1a1a1a;
    --text: #f5f5f5;
    --accent: #7b61ff;
    --border: rgba(255, 255, 255, 0.05);
}

This made theme switching trivial — just swap the variables. No duplicated CSS, no complex class toggling.

Search Performance

Typing in a search field shouldn't re-render 500 items on every keystroke. I debounced the input:

let debounceTimer;
searchInput.addEventListener('input', () => {
    clearTimeout(debounceTimer);
    debounceTimer = setTimeout(() => {
        renderProducts(filterProducts());
    }, 150);
});

150ms feels instant to the user but prevents unnecessary renders. This one line made the search feel dramatically smoother.

Cart with localStorage

The shopping cart persists across page reloads using localStorage. The pattern is simple:

function saveCart() {
    localStorage.setItem('hw-cart', JSON.stringify(cart));
}

function loadCart() {
    try {
        return JSON.parse(localStorage.getItem('hw-cart')) || [];
    } catch {
        return [];
    }
}

No backend, no login, no database. For a collector catalog, that's all you need. The cart lives in the browser — and it survives refreshes, tab closes, and even browser restarts.

What I'd Do Differently

Hindsight is 20/20. If I started over:

  1. Use a data file. Products are currently hardcoded in JS. A separate products.json would make updates easier.
  2. Add URL state. Filters should sync to the URL so users can share filtered views.
  3. Lazy load images from day one. I added loading="lazy" later — should have been there from the start.
  4. Write tests. Even a few unit tests for the filter logic would have saved debugging time.

Final Thoughts

Building a full catalog with vanilla JavaScript is absolutely doable. It's not always the right choice — but it's a fantastic learning exercise. You'll understand the DOM, event handling, and state management at a level that frameworks abstract away.

If you're building something similar: start simple, optimize later, and don't reach for a framework until you actually need one.
