How I Built FinBoard — A React Dashboard for Small Business

Building a small business dashboard with React, Vite, Recharts and live APIs. Architecture, API rate limits, and deployment without a backend.

Every small business owner I've talked to has the same problem: their numbers live in ten different places. Revenue is in a spreadsheet, crypto is in a wallet app, foreign invoices are tracked in a notes file, and ad spend is buried in Meta's dashboard. Nobody sees the full picture.

FinBoard started as a personal project — could I build a single dashboard that answers one question: "Am I making money this month, and where is it coming from?" It turned into my first real React application, and the first project in my portfolio that uses live third-party APIs.

Here's the whole story: why I chose React, how I structured it, what broke along the way, and what I'd do differently.

Why React (and Why Now)

My previous projects — the Hot Wheels Market, ZERNARIA — were built with vanilla JavaScript. That was intentional: no frameworks meant I learned how the DOM actually works. But at some point, the limitations become obvious.

A dashboard is stateful UI. Tabs switch, charts re-render, API responses come in asynchronously, and the whole interface reacts to user input. Doing this in vanilla JS means manually managing DOM nodes and event listeners everywhere. That's where React earns its place.

💡 Rule: Vanilla JS is great when the page is mostly static. React is great when the page is mostly state. FinBoard is 90% state — that's why React is the right tool here.

I also wanted to close a gap in my portfolio. I had "React" listed in my skills but no project to prove it. This was the moment to change that.

The Stack

Before writing a single line, I picked the tools. Here's what went in and why:

  • React 18 — components, hooks, no class syntax.
  • Vite — instant dev server, fast builds, zero config.
  • Tailwind CSS 3 — utility classes, dark theme, no separate CSS files per component.
  • Recharts — declarative chart library built for React.
  • Two public APIs — CoinGecko for crypto prices, open.er-api.com for currency rates.
  • No backend — everything runs client-side. GitHub Pages as host.

No Redux, no React Query, no fancy state manager. For a project this size, that would be over-engineering. Plain useState and useMemo are enough.

Architecture: Components First

The best part of React is how naturally you break things into pieces. My structure was obvious from day one:

src/
├── App.jsx              ← main layout, tab router
├── main.jsx             ← React entry point
├── index.css            ← Tailwind + global styles
├── hooks/
│   └── useApi.js        ← reusable data-fetching hook
├── data/
│   └── demoData.js      ← demo financials
└── components/
    ├── Sidebar.jsx
    ├── StatCard.jsx
    ├── RevenueChart.jsx
    ├── ExpenseChart.jsx
    ├── CryptoPanel.jsx
    ├── CurrencyConverter.jsx
    └── AdCalculator.jsx

Each component has one job. StatCard shows a number with a delta. RevenueChart renders the area chart. CryptoPanel fetches and displays the top 5 coins. If I need to change a color or layout, I open one file — not five.

The useApi Hook

Both CryptoPanel and CurrencyConverter need to fetch data from remote APIs. Instead of duplicating the loading/error/success logic, I wrote it once as a custom hook:

export function useApi(url, { intervalMs = 0, retryMs = 30000, transform } = {}) {
    const [data, setData] = useState(null);
    const [loading, setLoading] = useState(true);
    const [error, setError] = useState(null);
    const dataRef = useRef(null);

    const fetchData = useCallback(async () => {
        try {
            const res = await fetch(url);
            if (!res.ok) throw new Error(`HTTP ${res.status}`);
            const json = await res.json();
            setData(transform ? transform(json) : json);
            setError(null);
        } catch (e) {
            // If we already have data, keep showing it
            if (dataRef.current) return;
            setError(e.message);
        } finally {
            setLoading(false);
        }
    }, [url]);

    // ... effect with setInterval and auto-retry

    return { data, loading, error, refetch: fetchData };
}

Now both panels use the exact same code:

const { data, loading, error, refetch } = useApi(
    'https://api.coingecko.com/api/v3/simple/price?...'
);

Three lines. No repeated useState dance, no duplicated error handling. This is what people mean by "React helps you scale your code, not just your UI."

Charts That Don't Fight You

I tried three chart libraries before settling on Recharts. The problem with most of them is that they're built for dashboards — heavy, opinionated, and hard to theme.

Recharts is different. It's actually React components all the way down:

<AreaChart data={revenueData}>
    <defs>
        <linearGradient id="revGrad">
            <stop offset="0%" stopColor="#7b61ff" stopOpacity={0.5} />
            <stop offset="100%" stopColor="#7b61ff" stopOpacity={0} />
        </linearGradient>
    </defs>
    <CartesianGrid strokeDasharray="3 3" />
    <XAxis dataKey="month" />
    <YAxis />
    <Tooltip />
    <Area dataKey="revenue" stroke="#7b61ff" fill="url(#revGrad)" />
</AreaChart>

This reads like JSX because it is JSX. Any color, any gradient, any thickness — all controlled by props. Customizing the chart to match my dark palette took about 10 minutes.

When the API Rate Limit Hits

Halfway through testing, the Crypto panel started showing errors: Failed to fetch. The problem wasn't my code — it was CoinGecko's rate limit.

CoinGecko's free tier allows only about 10–30 requests per minute per IP. My auto-refresh was every 60 seconds, but during development I was hitting refresh constantly. Same IP, same limit — and every time I reloaded, one more request burned.

Here's what I did:

  1. Bumped the refresh interval from 60 seconds to 3 minutes. Crypto prices don't change dramatically in 3 minutes anyway.
  2. Silent fallback on error — if we already have data, keep showing it. A stale price is infinitely better than a red error banner.
  3. Auto-retry after 30 seconds — if a request fails and we have no data, try again automatically.
  4. Manual refresh button — for the user who wants to force it now.

The lesson: every external API will fail eventually. Design for the failure, not just the happy path.

💡 Production tip: Real apps don't hit public APIs directly. They route through a backend that caches the response, so the API is called once per minute regardless of how many users are on the site.

Dark Theme, Same Palette

I wanted FinBoard to feel like part of the same family as my portfolio, Hot Wheels Market, and ZERNARIA. That meant the exact same accent color #7b61ff, the same dark background #06060a, and the same typography — Syne for headers, Space Grotesk for body.

Tailwind made this trivial. Instead of using Tailwind's default colors, I defined custom tokens in tailwind.config.js:

theme: {
    extend: {
        colors: {
            bg: '#06060a',
            card: '#13131c',
            accent: '#7b61ff',
            'accent-light': '#9d8aff',
        },
        fontFamily: {
            display: ['Syne', 'sans-serif'],
            body: ['Space Grotesk', 'sans-serif'],
        },
    },
}

Now everywhere in the code I write bg-accent or text-accent-light — Tailwind resolves them to my brand colors. Change one line in the config, and the whole app updates.

Deploy Without a Backend

This is the part that still surprises people: FinBoard has zero server-side code. No Node.js backend, no database, no Docker. It's a static site.

Here's how deployment works:

  1. Write the React code in src/.
  2. Run npm run build — Vite compiles everything into a dist/ folder of HTML, CSS and JS files.
  3. Upload dist/ to GitHub Pages.
  4. Done. The site is live at 61simon.github.io/finboard/.

The browser handles all the API calls, all the state, all the rendering. The server just serves files.

This costs $0/month to host, scales infinitely (because it's just static files on a CDN), and requires zero maintenance. For a small business dashboard, this is more than enough.

What I'd Do Differently

Every project teaches you something you didn't expect. If I started FinBoard again today:

  1. Move the demo data into a form. Right now demoData.js is hardcoded. In a real product, users would enter their own numbers, and those would persist in localStorage or a database.
  2. Use URL state for tabs. Right now if you refresh the page, you're back on Overview. Better: sync the active tab to the URL hash so links are shareable.
  3. Add real charts for currency history. The converter only shows the current rate. A 30-day line chart would be much more useful.
  4. Use TanStack Query instead of custom useApi. My hook works, but TanStack Query (formerly React Query) does caching, retries, background refetching, and deduplication out of the box. In a real app, that's a no-brainer.
  5. Write at least one test. Even a single test for the AdCalculator math would have caught a bug where I mixed up two formulas.

Final Thoughts

FinBoard taught me more about React than any tutorial could. Because I wasn't following a step-by-step guide, every decision was mine — and every mistake was mine too.

The biggest lesson: frameworks don't make projects easier. They make them scalable. React isn't "faster to build" than vanilla JS — it's "easier to keep building." Once your UI has state, components, and async data, vanilla JS becomes a tangle. React keeps it organized.

If you're building something similar: start with a rough version. Make it work. Then refactor. Then make it pretty. The dashboard you see took three complete rewrites before it looked like this.
